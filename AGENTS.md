# AGENTS.md

Guidance for AI agents working in this repository. **This is a standalone Super
Productivity plugin repo, not the main `super-productivity` monorepo** — none
of Angular, NgRx, the op-log/sync pipeline, or `electron/` main-process code
lives here. If you're looking for that repo's `AGENTS.md`/`CLAUDE.md`, this
isn't it. (`CLAUDE.md` in this repo is a symlink to this file — there is only
one copy to keep in sync.)

## What this is

IMAP Inbox: watches one IMAP folder and turns every message that arrives
after setup into a Super Productivity task. Desktop-only (needs
`nodeExecution`). Ships independently as `plugin.zip` via GitHub releases —
never bundled with the app.

**[README.md](README.md) has the full design rationale** (protocol subset,
why the worker is a string, watermark semantics, known limitations). This
file is the terse, agent-facing complement — read the README for "why",
come back here for quick facts and invariants.

## Repo map

- `src/plugin.ts` — everything that touches `PluginAPI`: issue provider
  registration, the `taskCreated` hook, the credentials-UI message bridge,
  the menu entry
- `src/worker/` — the IMAP protocol client (`imap-client.ts`,
  `imap-parse.ts`, `mime.ts`, `mailbox-name.ts`); pure, no plugin API;
  `index.ts` is the entry point (`run(request)`), bundled twice by the build
- `src/host/` — watermark math (`watermark.ts`) and the message cache
  (`message-cache.ts`); pure, unit-tested
- `src/shared/` — types and key-derivation shared between host and worker
  (`types.ts`, `keys.ts`)
- `src/types/issue-provider-types.ts` — vendored shim for issue-provider
  plugin types; the published `@super-productivity/plugin-api@1.0.1` predates
  them upstream (see the file's own header comment) — this is intentional,
  don't delete it as "redundant" with the npm package
- `src/ui/index.html` — the credentials view (plain HTML/JS, no framework),
  reached from the app menu
- `scripts/build.js` — esbuild pipeline that produces the embedded worker
  string (see "Coupling with the host app" below); `scripts/package-zip.js`
  zips `dist/`
- `test/` — `fake-imap-server.cjs` (in-process IMAP server for integration
  tests), `*.test.cjs` (node:test), `fixtures/` (self-signed test cert)
- `dist/`, `dist-worker/`, `src/generated/` — build artifacts, gitignored,
  regenerated by `npm run build`

```bash
npm run typecheck         # tsc --noEmit — this is also what `npm run lint` runs (no ESLint here)
npm run build             # esbuild -> dist/ + dist-worker/ + src/generated/worker-source.ts

npm test                  # build, then vitest (*.spec.ts) + node --test (test/*.test.cjs)
```

Run `npm run typecheck` on every `.ts` file you touch before reporting work
done. `.prettierrc.json` / `.stylelintrc.mjs` exist at the repo root but
aren't wired into any npm script or installed as a dependency yet — pending
tooling, not an enforced check.

## Authentication / credentials

The password never travels through the (synced) issue-provider config — it
lives in the app's per-device secret store, reached only from `plugin.ts`
(host side), never from the iframe.

- **Storage:** `PluginAPI.setSecret(key, value)` / `getSecret` /
  `deleteSecret`, keyed by `imap-pw:${host}:${port}:${username}`
  (`secretKeyFor` in [`src/shared/keys.ts`](src/shared/keys.ts)). Host and
  username are normalized (trimmed, host lower-cased) before going into the
  key — the issue-provider config and the credentials-UI form must agree on
  host/port/username exactly, or the lookup misses.
- **Why not `configFields`:** anything in `pluginConfig` is synced state and
  lands in exports/backups; a password must never go there. This is also why
  the plugin can't enumerate its own provider instances (callbacks receive
  only `pluginConfig`, no instance id) — `rememberAccount()` in `plugin.ts`
  keeps its own non-secret account list in `persistDataSynced` purely so the
  credentials UI has something to list.
- **UI bridge:** `setSecret`/`getSecret` aren't available to iframe code.
  `src/ui/index.html` posts a message to `plugin.ts`'s `onMessage` handler
  (`getState` / `setPassword` / `clearPassword` / `testAccount`), which calls
  the real `PluginAPI` methods host-side. A stored secret is never echoed
  back to the UI — it only ever sees `hasPassword: true/false`.
- **User setup flow:** open "IMAP Inbox" from the app menu → fill
  host/username/port/folder/security/password → Save (or Test first, which
  accepts a typed password without saving anything) → create the actual
  issue provider under Settings → Issue integrations with the *same*
  connection tuple → set **Auto import to backlog** + a **default project** +
  polling mode **Always** (the manifest can only pre-select the first). Full
  narrative: README.md → Install / Credentials.
- **Known limitation:** the password is inlined into the spawned Node
  process's argv (`executeNodeScript` has no side channel for secrets) and is
  readable by other same-user processes. Use an app-password, not the
  account's primary password.

## Coupling with the host app

This plugin's build depends on exactly reproducing internals of the *main*
`super-productivity` repo's Electron host — not just its published
`plugin-api` package, which lags behind:

- `scripts/build.js`'s `HOST_SPAWN_PATH_PATTERN` must match
  `canExecuteDirectly`'s dangerous-pattern regex in
  `electron/plugin-node-executor.ts`, and the build's 80,000-char budget must
  stay under that file's 100,000-char hard limit — otherwise the worker
  silently runs in the `vm` sandbox (no `tls`, so no IMAP) instead of a
  spawned process, or the build fails outright.
- `plugin.ts`'s ambient `declare const PluginAPI` (`setSecret`/`getSecret`/
  `deleteSecret`, `onMessage`, `onReady`/`onUnload`, keyed
  `persistDataSynced`/`loadSyncedData`, `registerIssueProvider`, the
  `taskCreated` hook) reflects the *current* app source, not the published
  `@super-productivity/plugin-api@1.0.1` npm types. Confirmed against
  `master` and the `v19.0.1` release tag (checked 2026-09-16) — re-verify
  against the then-current release if this plugin ever stops loading on a
  real install.
- If either drifts upstream, this plugin breaks silently (wrong sandbox
  path) or loudly (`PluginAPI.x is not a function`) — there is no local way
  to detect that drift other than testing against a real, current Super
  Productivity build.

## Plugin-specific invariants

Full rationale is in README.md ("Gotchas worth knowing", "What counts as
'new'", "Marking imported mail as read"); this is the compressed version:

- Never write to stdout from worker code (`src/worker/**`) — that stream
  carries the JSON result the host parses.
- `lastUpdated` on a returned issue must be the message's immutable
  INTERNALDATE, never a value that can change — otherwise mail can overwrite
  edited task titles.
- Never set `state`, `start`, or `dueWithTime` on a mapped issue result — the
  host reads those as "done" or schedules the task.
- The watermark (`src/host/watermark.ts`) only ever advances to the highest
  UID actually handed to the host, never to UIDNEXT — a capped batch must
  leave the remainder for the next poll instead of skipping it.
- `persistDataSynced` writes (watermark, remembered accounts) are
  last-write-wins across devices; skip the write when nothing changed
  (`isWatermarkUnchanged`, the serialization check in `rememberAccount`)
  rather than persisting identical state on every poll.
- Mark-as-read must stay a local-only side effect of the `taskCreated` hook
  — a task arriving through sync must never re-trigger it.

## Testing

- Unit (`*.spec.ts`, vitest): pure modules only — parsing, watermark
  transitions, the cache, key derivation.
- Integration (`test/*.test.cjs`, node:test): the real built worker bundle
  against `test/fake-imap-server.cjs`, plus `host-script.test.cjs`, which
  spawns the shipped script exactly as the Electron host does.
- **Known gap:** nothing here has run against a real IMAP server
  (Gmail/Outlook/Dovecot/Proton Bridge) — all protocol coverage is against
  the hand-rolled fake server. A real-server test is the thing this suite
  cannot substitute for, not something redundant with it.
